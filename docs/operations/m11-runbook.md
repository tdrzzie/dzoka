# M11 operations and deployment

Current-account local profile, 2026-11-26. [M11 verification](../testing/m11-verification-2026-11-26.md) defines executed scope and remaining acceptance. This guide adds to the historical [local readiness guide](local-readiness.md); it does not replace its worker/model pins or enable deferred providers.

## Deploy the packaged core

Build with the reviewed JDK/Maven and locked artifacts, run the audit/dependency/native gates, then run `python -B tools/prepare_core_image.py`. The output directory must be fresh; retain or remove only the generated `target/core-layer` between builds. Build `docker build -f deployment/core.Dockerfile -t <your-reviewed-image> .` from the repository root. The Docker context allowlist contains only the packaged classes and locked libraries, including their embedded notices. No credentials, source audit cache, private models or test state enter the image.

The Compose profile provisions a **fresh** PostgreSQL database with separate control, migration and application accounts. Do not point its initializer at an existing installation. Prepare two protected directories outside source control:

| Directory | Required files | Readers |
|---|---|---|
| DB secret directory | `control`, `migrator`, `app`, each containing an independent strong password | Database initializer; migrator receives only its own file |
| App configuration directory | `spring.datasource.password` matching `app`; approved Spring properties as separate files | API identity only |

Set `DZOKA_CORE_IMAGE`, `DZOKA_DB_SECRETS_DIR`, `DZOKA_APP_CONFIG_DIR`, `DZOKA_NETWORK_SUBNET`, `DZOKA_OIDC_ISSUER`, `DZOKA_OIDC_JWK_SET_URI`, `DZOKA_OIDC_AUDIENCE`. Select a private subnet after checking host routes and Docker IPAM; this host has exhausted automatic pools. Use HTTPS identity endpoints. Run `docker compose -f deployment/compose.yaml config --quiet`, then `docker compose -f deployment/compose.yaml --profile replicas up -d`. Omit `replicas` for a single local API. Ports bind loopback; configure a reviewed TLS gateway for remote access. The private bridge is not a production TLS/network-isolation substitute. The database is a single-host volume, not an HA service.

The app secret directory may supply `dzoka.recovery.hmac-key`, approved provider properties and per-provider secret-file paths. Never mount the whole DB secret directory or Docker socket into the core. Missing required properties fail startup. Runtime `dzoka_app` must remain a nonowner, non-superuser and non-BYPASSRLS role. Migration runs once as a separate container and must finish successfully before APIs start. No default tenant, membership or password is created. Provision reviewed local memberships through a separate privileged administrative process. The test-only `ProbeIssuer` is not part of the image or production deployment.

For Kubernetes, supply the approved **core image digest**, distinct existing `appSecret` and `migrationSecret`, target egress CIDRs and gateway labels to `deployment/helm/dzoka`. App Secret keys are Spring property filenames, including database URL/user/password and issuer/JWKS/audience. Migration Secret keys are `DZOKA_MIGRATION_URL`, `DZOKA_MIGRATION_USER`, `DZOKA_MIGRATION_PASSWORD`. Enable database TLS with certificate/hostname validation outside the local test network. The chart requires two replicas, drops capabilities, disables API tokens, bounds resources, uses startup/readiness/liveness probes, spreads pods, provides a disruption budget and restricts network ingress/egress. A separate migration network-policy hook precedes the migration job. Target CNI policy enforcement, DNS, storage, TLS, cluster scheduling and rolling-upgrade rehearsal must be verified in the actual cluster; rendering alone proves none of these.

Existing model, raster, edge, channel, federation and fulfillment workers retain their reviewed separate identities, configurations and scheduling contracts. Use their operation guides. This chart does not grant decoder containers a Docker socket, bundle unreviewed IdP/broker/storage images, download model weights or replace an unavailable provider with a fixture.

## Learning and model changes

All routes below are under `/api/v1/tenants/{tenant}` and require a valid JWT plus local permission. Responses containing learning/operations data use `Cache-Control: no-store`.

1. An independent `learning:review` identity writes `/learning/policy` with explicit `version`, `optIn`, `requireGate`, `retentionDays` and `purposeSha`. **Set `requireGate=true` before production model changes.** Production defaults reject activation without this policy and reject an existing active model lacking the governed policy. `dzoka.learning.allow-legacy-rollouts=true` is an explicit older-fixture compatibility exception; production keeps it false. Lexical searches with no active model remain available.
2. A search participant with `feedback:submit`, `matches:read` and report access declares `/learning/feedback/{id}` using their own durable search client ID, candidate and explicit boolean `positive`. Claim approval/rejection and confirmed recovery also capture minimal feedback transactionally. Rejection does not establish that two objects differ; recovery does not establish a pair label without independent adjudication.
3. A different `learning:review` identity writes immutable `/learning/adjudications/{id}`: feedback, monotone revision, `POSITIVE`, `NEGATIVE` or `UNAVAILABLE`, independently attested institution-group digest and evidence digest. Raw ownership answers are never dataset fields.
4. `learning:manage` freezes `/learning/datasets/{id}` with latest adjudications, TRAIN/VALIDATION/TEST membership and purpose. Item/candidate identities and declared institution groups cannot cross splits; earlier recorded feedback must precede later observed cohorts. Source revisions, availability, opt-in version, expiry and revocation are rechecked. Matching datasets require a real paired candidate; native ownership/recovery feedback without a candidate cannot become matching truth. Institution grouping is an accountable curator attestation because current reports do not carry an independently verified institution association. These checks cannot prove the truth of an external label or group assertion.
5. Record a paired experiment against the exact TEST cohort and native sealed rollout, model artifact/configuration and evaluation hashes. Unknown predictions remain unavailable, rank zero means observed but not retrieved. Metrics include coverage, conditional positive Recall@K, a missing-evidence recall lower bound, paired precision, single-relevant-item MRR/NDCG, false-match/negative rates and Brier error where probabilities exist. This is bounded pair evaluation, not complete corpus ground truth or a claim of calibrated ownership safety. Production representative slices and qualified outcome review remain required.
6. Independent approval checks recorded thresholds, complete probability coverage, baseline non-regression and TRAIN/TEST separation. Native rollout seal/source checks and compare-and-swap activation/rollback remain in force. Approval never authorizes release. Revoking a dataset/experiment, changing labels or source revisions, opt-out or expiry invalidates governed use; matching fails closed while an active rollout lacks valid evidence. Activate an independently approved valid rollback, or restore permitted evidence through an explicit new version. Do not lower thresholds to hide a failed screen.

The registry is append-oriented in PostgreSQL. Optional MLflow export uses fixed-origin REST, stable operation tags, bounded responses and reconciliation before recreating an uncertain remote run/model version. It exports dataset/model/config/evaluation digests and aggregate metrics, not case rows or private input. Model sources use the explicit metadata reference `dzoka://models/sha256/{digest}`; this is not a generic MLflow-downloadable weight bundle. `/learning/mlflow/sync-activation` mirrors the native activation/rollback into the descriptive `observed-native-active` alias and availability tags. Remote aliases and server responses cannot authorize native promotion. Consumers must recheck native policy; a suspended tag is not a valid model rollout.

Configure `dzoka.mlflow.origin`, numeric `dzoka.mlflow.experiment-id` from an existing permitted experiment, and optional `dzoka.mlflow.token-file` holding an independent backend bearer credential. The backend must separately approve its version, authentication, authorization, retention and artifact resolver. Export rows bind their backend origin/experiment digest; changing the destination does not reuse another server's run or model-version IDs. Use a new explicit experiment export for a new destination. No credentials are discovered automatically. An absent origin leaves this optional integration unavailable; it does not silently emulate MLflow. Schedule bounded `tools/operations_worker.py --action mlflow`, then `--action activation`, with a private service-token file and `learning:manage`/`fingerprints:manage` permissions. API export faults retain pending work; reconcile rather than blindly repeat remote creation. Duplicate remote matches fail closed for operator investigation.

## Telemetry, analytics and alerts

Configure `dzoka.otlp.origin` and optional `dzoka.otlp.token-file` for an approved OTLP HTTP/JSON collector. Only explicitly enabled loopback tests permit plain HTTP. Request spans accept valid nonzero W3C trace IDs, create fresh span IDs, and export framework route templates, method and status. The producer also exports fixed-message structured logs and bounded global counters. It excludes request bodies, URI/query values, JWTs, contacts, ownership evidence, actor/tenant labels and provider error bodies. A 128-entry queue and one daemon exporter bound memory/concurrency. Collector failures/drop counts are visible in later exported metrics; diagnostic loss never changes domain success. Domain security/custody audit remains durable and unsampled in PostgreSQL.

HTTP diagnostic context has nested core transaction spans and is retained in outbox, AI/perception jobs, search history, recovery activity and external-operation metadata. The outbox dispatcher restores persisted context across publication/acknowledgment and always cleans thread state. A `telemetry:export` identity can schedule the bounded operations worker `telemetry` action to export completed AI/perception/external-operation lifecycle spans under their original enqueue trace. These durations include queue time. Export is deliberately lossy and never carries job inputs/results or case IDs; it does not instrument the inside of every third-party model/SDK process. `/health/live` reports the process; `/health/ready` checks database connectivity only. Neither says that models, a tenant's restore barrier or external providers are ready.

`operations:read` can read `/operations/status`: pending AI/outbox counts, uncertain/blocked external operations, restore closure and current model-evidence availability. `analytics:read` can read `/operations/analytics?since=<instant>` over current available reports in a UTC-day-created cohort. Categories are allowlisted, locations use coarse one-degree cells and loss times use only intervals within one four-hour UTC bucket. Group outputs below five are suppressed, not anonymized with a differential-privacy guarantee. Returned-item denominators, backlog, completed mean/median times, courier and reward use remain separate from fraud and ownership false-positive rates. Independent safety/fraud/attribution metrics use the outcome audit contract below. Missing or undersized known denominators are explicitly unavailable, never zero.

| Signal | Operator action |
|---|---|
| Readiness unavailable | Check DB reachability, TLS, pool and credentials; preserve durable jobs; never switch to an in-memory authority |
| Outbox/AI backlog grows | Inspect authorized oldest jobs, leases and provider readiness; pause new optional work or scale reviewed workers; retain idempotency identities |
| External operation UNKNOWN/SENDING | Reconcile the stable provider operation before retry, cancellation or payout |
| Model evidence unavailable | Stop governed search, inspect source/consent/approval status and use an approved native rollback |
| Restore blocked | Finish tombstone replay, canonical/media purge and identity/projection review before opening |
| Telemetry exports fail/drop | Check the collector and its access/retention policy; protect disk/queue limits; domain audit remains authoritative |

Choose actual alert durations, SLOs and capacity budgets from the target workload. Local small-race latency is a diagnostic, not a production availability or retrieval-capacity benchmark.

## Independent outcome audits

A separately provisioned `analytics:adjudicate` identity reads `/operations/outcomes/{claim}` and appends `/operations/outcomes/{claim}/audits/{id}`. Records require a monotone revision, current source digest, `OWNER`/`NOT_OWNER`/`UNAVAILABLE`, `CONFIRMED_FRAUD`/`NO_FRAUD`/`UNAVAILABLE`, `LOCAL`/`FEDERATED`/`UNAVAILABLE` contribution and reviewed evidence digest. Claimants and original native decision reviewers cannot audit their own decision. Source bindings include the report version, intake generation, decision and latest native review; changed, held or deleted sources invalidate eligibility without rewriting the audit.

Analytics uses the latest eligible independent audit per current claim. Ownership decision FPR divides approved/returned known nonowners by all known nonowners, including rejected claims. Adjudicated fraud rate divides confirmed fraud by explicitly known fraud outcomes. Federation contribution is the independently attributed share of returned known-owner claims with known contribution; it is not a cross-node score or automatic attribution claim. Each known denominator needs at least five observations. Corrections append a new audit revision, including unavailable truth when evidence is withdrawn. No audit changes a claim, custody, grant or release permission. The application cannot prove the truth or qualification of an external human attestation; representative permitted institutional evidence and qualified review remain acceptance requirements.

## Retention and restore

`retention:manage` can version-audit `/operations/policy` with report retention days, daily actor/tenant report-write budgets and an evidence digest. New reports use the current retention duration; changing it does not silently rewrite old evidence expiry. Create/revision replay does not consume a new budget, concurrent distinct writes share persisted UTC-day limits, and exhaustion returns HTTP 429. Other existing classes retain their explicit policy contracts: short verification sessions, private search history, camera grants/indexes, model artifacts, relay/passport expiry and legal holds. Audit/custody/tombstones are retained separately, not erased along with raw evidence. Institution-specific durations and legal requirements need review; there is no universal production policy.

Use the bounded operations worker actions `reports-purge`, `fingerprints-purge`, `perceptions-purge`, `history-purge`, `learning-purge` with only their required maintenance permissions. Continue the separate media worker for actual private-object deletion and cleanup acknowledgments, plus existing channel/passport/edge/federation purges. Expired learning membership remains protected while either paired source has a legal hold. Workers must not claim a deletion complete while an object backend is unavailable. Retry safely and inspect authorized state. A maintenance identity acting during a restore also needs `retention:recover`.

For a coordinated backup:

1. Quiesce or establish a documented cross-service checkpoint. Create a real PostgreSQL custom-format backup with ownership/ACLs, preserve compatible role provisioning, and retain WAL/PITR state if the target RPO requires it. Capture outbox/inbox and operation reconciliation state in the same authority snapshot.
2. Snapshot permitted object bytes and inventory, including version/deletion state, separately backed up nonsecret configuration, schema/artifact/profile manifests and the **latest** tenant erasure journals. Keep secrets encrypted in independently controlled escrow with key/version references. Never put plaintext secrets or private backup bytes in Git.
3. Stage explicit files in a protected directory. `tools/backup_bundle.py seal` requires inventory entries for `postgres`, `objects`, `configuration`, `tombstones`, a checkpoint digest and separate secret-escrow digest. Preserve its manifest digest in independent trusted storage. `verify --expected-sha` rejects changed/missing entries, traversal and links. A digest verifies integrity, not permission, encryption, checkpoint consistency or secret recoverability.
4. Restore offline to independent storage with APIs/workers blocked. Validate archive, rows/catalog, ownership/RLS, policies, keys and object hashes. Reapply all later erasures before rebuilding permitted indexes. Do not replay paid/shipping effects from an old snapshot; reconcile their stable external IDs first.
5. As the tenant's `retention:recover` identity, close `/operations/restore/close`, import the authoritative erasure manifest at `/operations/restore/replay`, run canonical/derived/object maintenance and review current identities/configuration/projections. Valid legal holds cause a conflict requiring policy resolution. Opening `/operations/restore/open` requires the exact replay manifest digest, separate identity/configuration and projection review digests, and no pending known canonical erasure artifacts. Reviews are explicit operator attestations, not automatically proven external work. Barrier changes append an operational audit record. Closing waits for in-flight tenant transactions; ordinary reads/writes/workers cannot pass a closed barrier. Restrictive report RLS also applies to restoration identities: a tenant-local tombstone import cannot read, change or erase another tenant's report.

Export the tenant's latest journal via paginated `/operations/erasures?after=<last-report-uuid>`. UUIDs are private operational metadata, not public telemetry. Missing current reports still retain tombstones. A fresh offline restored DB must start behind network/worker controls: an online barrier cannot retroactively protect data already served before closure. Verify all tenant barriers and disabled/removed memberships before opening ingress.

The automated restore exercises exact native PostgreSQL row/catalog equality and a staged bundle with an explicitly empty object inventory. A separate real private-S3 test restores older synthetic image bytes behind the closed tenant barrier, reapplies a later erasure, rejects reopening until canonical and acknowledged object cleanup finish, and proves the old bytes unavailable. This is not a coordinated multi-service production snapshot. Multi-host failure, encryption/secret-escrow recovery, target S3 semantics and production PITR/RPO/RTO need target rehearsal. No local pass substitutes for those results.

## HA and upgrade decisions

Core APIs and federation gateways can run stateless replicas behind the reviewed TLS gateway. Worker leases/retries and outbox/inbox preserve idempotency during restarts. Use a separately reviewed PostgreSQL replication/failover system with one authoritative writer, fencing and tested WAL/PITR recovery. Kafka requires replicated quorum/ISR and consumer replay/DLQ policy. Object storage needs authorized replication, retention/deletion propagation and reconciliation. Optional Redis and vector indexes remain disposable projections with canonical rebuild and tenant filters; never promote a restored stale index before tombstone replay. AI workers need capacity reservations and immutable model/configuration pins; more API replicas do not add model capacity. Federation nodes retain independent PII custody and key rotation.

Back up before migrations. V25 is additive but this core requires its barrier schema; deploy migrations before new replicas. The chart defaults to a fenced `Recreate` upgrade: older pre-M11 binaries do not enforce these new governance/restore barriers and must not serve alongside the new contract. Enable `compatibleRollingUpgrade` only after proving both exact releases enforce the same contracts and testing their coexistence at the target. Application rollback must use a release that enforces the current barrier/governance contracts, retain V25 and append-only history; do not downgrade/drop security columns or erase migration history to force a rollback. Perform a restore to a separately validated prior release if an incompatible schema correction is unavoidable. The local rehearsal proves one API survivor, API restart and single-host DB restart; it does not simulate multi-host DB failover or establish an uptime/RPO/RTO objective.
