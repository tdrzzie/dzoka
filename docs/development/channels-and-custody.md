# WhatsApp, anonymous relay and staff custody

## Configure the channel

Configure one WhatsApp tenant per Core deployment. Set `DZOKA_WHATSAPP_TENANT`, `DZOKA_WHATSAPP_ACCOUNT`, `DZOKA_WHATSAPP_PHONE_ID`, `DZOKA_WHATSAPP_GRAPH_VERSION`, `DZOKA_WHATSAPP_VERIFY_TOKEN`, `DZOKA_WHATSAPP_APP_SECRET`, `DZOKA_WHATSAPP_ACCESS_TOKEN` and `DZOKA_WHATSAPP_CONTACT_KEY`. The contact key is a 32-byte random key encoded in hex. Store these values through the deployment secret manager and retain the contact key securely for restores. Keep the Graph origin set to Meta in deployment. The alternate origin is limited to explicit loopback tests.

Subscribe the tested business account to the WhatsApp messages field at `/api/v1/hooks/whatsapp`. The Core uses the verify token only for the handshake and the application secret for signed callbacks. Provision the local service identity `urn:dzoka:channel` / `whatsapp` with active `channels:service` membership in the configured tenant. Give the scheduled dispatcher its own authenticated tenant membership with the same permission.

Create the corresponding approved fixed templates before sending. The default prefix is `dzoka_` and the default locale is `en_US`. Override them with `DZOKA_WHATSAPP_TEMPLATE_PREFIX` and `DZOKA_WHATSAPP_TEMPLATE_LOCALE`. Template suffixes are `help`, `report_saved`, `relay_update`, `recovery_update`, `match_alert` and `unsupported`. Use generic text for match alerts that asks the recipient to reply `SEARCH` to their report. Keep descriptions, contacts, claim answers, pickup secrets and precise locations out of templates. Bounded text responses to a signed message can dispatch for up to 23 hours after that message. The queue encrypts their bodies and clears them on terminal delivery or cancellation. [Meta message reference](https://developers.facebook.com/documentation/business-messaging/whatsapp/reference/whatsapp-business-phone-number/message-api).

## Use the channel

Authenticated paths are relative to `/api/v1/tenants/{tenant}/channels`.

1. A `channels:admin` operator verifies the account-to-number binding and consent out of band. Use `PUT /contacts/{id}` with `subject`, the international digits in `address`, and `consentConfirmed: true`. A linked participant needs `reports:write` to submit an intake report. The subject is interpreted under the authenticated issuer.
2. Participants can send `LOST <description>`, `FOUND <description>`, `HELP`, `RELAY <thread UUID> <phrase>` or `STOP`. Text reports enter the same private intake as the web API. Send a location as a quoted reply to the original report message to add a revision. The linked account needs `reports:read` and `reports:write` for this operation. Pins with no reported accuracy use the Core's maximum supported uncertainty radius. A revision submitted elsewhere takes precedence over a stale reply. Phone addresses are encrypted at rest.
3. A reviewer holding `channels:moderate`, `recovery:review` and `reports:read:any` opens a relay with `PUT /relays/{thread}` and `claim`. Only the linked claimant and found-report author participate. The approved phrases are `REQUEST_UPDATE`, `READY_TO_ARRANGE_PICKUP` and `THANK_YOU`. Participants can also post to `PUT /relays/{thread}/messages/{id}`. Use `PUT /relays/{thread}/block` with `abuse` to stop further relay activity and optionally flag it for a moderator.
4. A participant with `channels:use` may revoke consent with `DELETE /consent` or through signed WhatsApp `STOP`. Re-enable only with renewed verified consent through `PUT /contacts/{id}/consent`. A moderator can inspect flagged threads via `GET /relays/{thread}/moderation` and prune expired entries with `POST /relays/prune`. Relays are usable for at most seven days. Abuse evidence has a further 30-day review window.
5. Run `POST /dispatch` from the authorized scheduler. Each call performs bounded maintenance and dispatches at most one notice. App users can inspect their own recent notification states via `GET /notices`. An already submitted message may still deliver after opt-out. Queued messages are checked again before dispatch. A network failure or uncertain response goes to `UNKNOWN` for reconciliation. It does not cause a second send. Explicit throttling allows up to three attempts with a minimum one-minute delay.

## Attach media, search and arrange pickup

- Reply to the original report message with a PNG or JPEG photo, voice note or video up to 5 MiB. The dispatcher takes one pending attachment per call, fetches the current media URL with the provisioned phone-number ID, and checks the signed digest and expected size before storing the private object. Photos follow the existing isolated raster worker. Voice and video stay quarantined with no playback, preview or transcription. [Meta media lookup](https://www.postman.com/meta/whatsapp-business-platform/request/ptjyi84/retrieve-media-url), [Meta media download](https://www.postman.com/meta/whatsapp-business-platform/request/zsq66eh/download-media).
- A desk operator with `channels:admin`, `recovery:manage` and report access publishes a found-item offer using `PUT /match-offers/{report}` with `revision`, `summary` and `enabled`. Use a short, non-sensitive summary appropriate for matching. Publish a new revision after reviewing it, or disable the offer to withdraw it. The channel uses the summary in matching and keeps it out of replies.
- Reply to an original lost report with `SEARCH`. The linked account needs `reports:read` and `matches:read`. Use the returned run reference and candidate number in a quoted `REVIEW <run> <number>` or `CLAIM <run> <number>` reply. Search applies the Core lexical scorer to the member's own lost report and up to 512 published offers. Candidate review rechecks current eligibility, uses the same report and contact as the search, and expires after 24 hours. Claims additionally require `claims:submit`.
- Follow the claimant-only `CHALLENGE <intake> <claim>` and `ANSWER <intake> <claim> <session> <answer>` instructions. Answers are assessed by the existing recovery service. The channel queue retains neither the answer nor the result of the private comparison. The claimant receives a receipt for submission and staff review the assessment through the protected Core API. WhatsApp itself handles the inbound message, so use the authenticated Core path for users who cannot share challenge responses with the channel provider.
- Send `PICKUP <intake> <claim>` to request pickup after approval. A staff member with `recovery:handover` reads the request at `GET /api/v1/tenants/{tenant}/recovery/intakes/{intake}/pickup-messages`. Staff then use the existing pickup context and return endpoints for a valid staff-bound token and recipient confirmation. Send `CONFIRM <intake> <claim>` after staff record the return to acknowledge it.
- The dispatcher checks one due lost-report watch per call. A lost report entered in WhatsApp after V19 adds a watch. A quoted search adds one for an earlier WhatsApp report while its signed inbox anchor is retained. A newly seen candidate with comparable evidence can trigger a generic alert. Stable candidate and report references prevent repeat notices from the same pair. Confirmed opt-out pauses scans and cancels queued sends. Additional channel providers and business-scoped identities with no verified telephone route require separate transport support.

## Staff custody

Use a scoped `custody:operate` membership and the path `/api/v1/tenants/{tenant}/recovery/intakes/{intake}/custody`. Read the projection and its recent history with `GET`. Submit `PUT /{event}` with the action, current `expectedGeneration`, opaque `destination` site, `observedAt` in UTC with at most microsecond resolution, and an `evidenceSha` reference to protected local evidence. Keep the event UUID and payload for exact replay.

Use `STORE` for a location change under the same custodian. Use `INCIDENT` to record an incident and place a hold. To hand off to another operator, use `REQUEST_TRANSFER` with the receiving operator's `recipientRef`. That operator submits `ACCEPT_TRANSFER` with the original request UUID as `requestId`, the same proposed location and the original expected generation. A recorded `OFFLINE_CONFLICT` requires an operator to reconcile the physical evidence with the current projection before issuing a new request. Existing staffed pickup remains the return authority.
