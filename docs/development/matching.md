# Private matching on the current setup

The matching endpoint is `GET /api/v1/tenants/{tenant}/internal/matching/reports/{report}/candidates`. `limit` defaults to 10 and accepts 1 through 20. An optional `spaceId` selects one active text embedding space. The source and candidates must be live current revisions of opposite report kinds. A matcher needs `matches:read` and `reports:read` and must own a report or have `reports:read:any` to use it. Access granted for another purpose such as fingerprint administration does not widen matching scope.

The response contains route status, ranks, candidate and revision identifiers, model-space and component provenance where applicable, similarity, coverage and disposition. Treat `CONFLICT` as a hard veto and `UNCALIBRATED` as a heuristic evidence result. A bounded result may be partial or truncated. A pool of more than 512 visible reports is rejected with `CAPACITY_EXCEEDED`. Use the result to review possible matches. Matching does not authorize an entitlement or item release.

`POST /api/v1/tenants/{tenant}/internal/matching/reports/{report}/identifier-attestations` accepts `revision`, `keyVersion`, `scopeDigest`, `digest` and `attestationId`. A verifier must hold `matches:attest-identifiers` and independent report access. Use a tenant-keyed, domain-separated HMAC for the verified manufacturer scope and another for its canonical serial, delivered by a trusted issuer. Never send the raw serial or grant this permission to general report submission or OCR accounts. An attestation is immutable for a report revision. A new key version or scope is incomparable to a different version or scope.

`dzoka.matching.vector-backend` supports `exact` for native local development, `pgvector` for the reviewed `public.vector` extension, and `qdrant` for a separately managed local projection. Qdrant reads `DZOKA_MATCHING_QDRANT_ORIGIN` and `DZOKA_MATCHING_QDRANT_API_KEY`. The origin must be an explicit port on `http://127.0.0.1`. Name the collection `dzoka_{spaceKey}` with cosine vectors sized for that space. Use the immutable component UUID as point ID, with `tenant` and `space` payload fields. Missing points fail the vector route and leave the other routes usable. Projection automation and production approval are outstanding. See [ADR 0053](../adr/0053-bounded-matching-and-vector-backends.md).

Run `python -B tools/matching_calibration.py --plan <private-json> --sha256 <plan-hash> --output <new-private-json>` for an offline calibration draft. The plan binds `schemaVersion` (1), `datasetSha256`, `spaceKey`, `scoringVersion` (`bounded-evidence-v1`), `minimumCoverage` and `cases`. Each case records `caseSha256`, `groupSha256`, `split` (`fit` or `holdout`), boolean `label`, `similarity`, `coverage` and `disposition`. Supply review-owned hashes for the evaluation cases and entity groups. The tool refuses declared group overlap, measures holdout Brier error on the same supported cases as the raw score, and reports uncovered bins. Neither a synthetic fit nor a labeled draft changes the live confidence field.

### Index and maintenance

On a reviewed pgvector deployment, apply [the index DDL](../../tools/m5_install_pgvector_index.sql) after Flyway as the approved owner. Run it in autocommit with stop-on-error. Set `dzoka.matching.vector-backend=pgvector-indexed` only after the index is valid. The HNSW expression index serves 384-dimensional non-truncated text components and is maintained by PostgreSQL when authoritative rows change. Observe its readiness and measure target recall before cutover. Verify `pg_index.indisvalid` and `indisready` after a build. If an interrupted build leaves an invalid index, have the owner remove that exact invalid index concurrently and apply the reviewed script again. Keep independent scoped recall tests during maintenance and rebuild. The selected indexed route fails visibly when the extension or index is unavailable. Above the exact pool limit, indexed vector and verified-serial candidates remain available and the other routes report capacity. An approximate result always carries the approximate or truncation status.

For Qdrant, provision a cosine collection per space before activation. Give the core its read credential and use `DZOKA_MATCHING_QDRANT_WRITE_KEY` for reconciliation. A principal with `matches:maintain-projection`, `reports:read`, and `reports:read:any` may call `PUT /api/v1/tenants/{tenant}/internal/matching/projections/{space}`. It upserts the tenant’s active components in bounded batches and deletes stale points only within that tenant and space. A failed pass can be replayed idempotently. Schedule the operation after rollout changes, revisions, and erasures, plus regular reconciliation. A disabled but retained space can be reconciled to an empty set. Retire a whole collection only under the database and projection operator’s separate lifecycle controls.

### Durable history

Use `PUT /api/v1/tenants/{tenant}/internal/matching/reports/{report}/runs/{run}` with a client-generated UUID and an object containing `spaceId` (optional) and `limit` (1–20). Repeat the same UUID and parameters within the 24-hour retention window to replay the saved result. Changed parameters conflict. Use `GET` on the same URI to retrieve a recorded search. Each result is private to its original actor. If any referenced report is expired, superseded, deleted, or outside current scope, history returns 404. An erased source revision cascades the run, and an erased candidate revision cascades its candidate row and invalidates replay. The ledger stores scored evidence and opaque references. Source text, protected digests and raw vectors are omitted.

Call `POST /api/v1/tenants/{tenant}/internal/matching/history/prune` with `matches:maintain-history` to remove up to 200 expired runs per call. The matching maintenance runner accepts a protected hash-bound JSON plan with `schemaVersion`, `origin`, `allowLoopbackHttp`, and `assignments`, each containing `tenant`, `spaces`, and `pruneHistory`. Run `python -B tools/matching_maintenance.py --plan <file> --sha256 <digest> --credentials <file>` with an independently issued Core JWT in the private `token` field. Use an approved scheduler and have it alert on an incomplete pass. The runner is serial and bounded and reports aggregate completion counts. Target scheduler, credential rotation and alerting need deployment configuration.
