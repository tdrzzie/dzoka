# Private matching on the current setup

The matching endpoint is `GET /api/v1/tenants/{tenant}/internal/matching/reports/{report}/candidates`. `limit` defaults to 10 and accepts 1 through 20. An optional `spaceId` selects one active text embedding space. An optional `category` restricts candidates to that exact declared category. Intake accepts a revision-scoped category code of up to 48 uppercase letters, digits and underscores, starting with a letter. Earlier revisions without a declaration remain searchable through unfiltered routes. The source and candidates must be live current revisions of opposite report kinds. A matcher needs `matches:read` and `reports:read` and must own a report or have `reports:read:any` to use it. Access granted for another purpose such as fingerprint administration does not widen matching scope.

The response contains route status, ranks, candidate and revision identifiers, model-space and component provenance where applicable, similarity, coverage and disposition. Treat `CONFLICT` as a hard veto and `UNCALIBRATED` as a heuristic evidence result. Each route returns up to 20 results and reports its own availability and truncation. At most 20 fused candidates reach detailed reranking. Joint image/image and image/text comparisons use live, compatible pins from the active perception rollout and return component references and modality names. Category affects retrieval and filtering only. Matching results help review possible matches. Ownership and release require their own authorization.

`POST /api/v1/tenants/{tenant}/internal/matching/reports/{report}/identifier-attestations` accepts `revision`, `keyVersion`, `scopeDigest`, `digest` and `attestationId`. A verifier must hold `matches:attest-identifiers` and independent report access. Use a tenant-keyed, domain-separated HMAC for the verified manufacturer scope and another for its canonical serial, delivered by a trusted issuer. Never send the raw serial or grant this permission to general report submission or OCR accounts. An attestation is immutable for a report revision. A new key version or scope is incomparable to a different version or scope.

`dzoka.matching.vector-backend` supports `exact` for native local development, `pgvector` for exact use of the reviewed `public.vector` extension, `pgvector-indexed` for the reviewed production index, and `qdrant` for a separately maintained local projection. Qdrant reads `DZOKA_MATCHING_QDRANT_ORIGIN` and `DZOKA_MATCHING_QDRANT_API_KEY`. The origin must be an explicit port on `http://127.0.0.1`. Name the collection `dzoka_{spaceKey}` with cosine vectors sized for that space. Use the immutable component UUID as point ID, with `tenant` and `space` payload fields. Missing points fail the vector route and leave the other routes usable. [ADR 0053](../adr/0053-bounded-matching-and-vector-backends.md).

Run `python -B tools/matching_calibration.py --plan <private-json> --sha256 <plan-hash> --output <new-private-json>` for an offline calibration draft. The plan binds `schemaVersion` (1), `datasetSha256`, `spaceKey`, `scoringVersion` (`bounded-evidence-v1`), `minimumCoverage` and `cases`. Each case records `caseSha256`, `groupSha256`, `split` (`fit` or `holdout`), boolean `label`, `similarity`, `coverage` and `disposition`. Supply review-owned hashes for the evaluation cases and entity groups. The tool refuses declared group overlap, measures holdout Brier error on the same supported cases as the raw score, and reports uncovered bins. Neither a synthetic fit nor a labeled draft changes the live confidence field.

### Calibration review

Under `/api/v1/tenants/{tenant}/internal/matching/calibrations/{artifact}`, an identity with `matches:propose-calibration` uses `PUT` to submit a draft at a new UUID. Submit the evaluator fields `spaceKey`, `scoringVersion`, `planSha256`, `datasetSha256`, `minimumCoverage`, `holdoutCount`, `supportedHoldout`, `holdoutBrier`, `rawScoreBrierOnSameRows` and `bins`. Include `spaceId`, `activationVersion`, `sourceKind` and the evaluated `vectorBackend` (`EXACT_ROUTE`, `PGVECTOR_EXACT`, `PGVECTOR_HNSW` or `QDRANT_EXACT`).

A separate identity with `matches:review-calibration` may read that draft and use `PUT /approval` with `reviewSha256`, `maximumBrier`, `minimumBinSupport` and `validHours` (1–720). Approval requires the current rollout, read permissions for the reviewed scope, complete holdout support and an improvement over raw similarity within the reviewed error threshold. The latest approval applies only to unfiltered tenant-wide text matching in the approved scope, with a comparable outcome and supported bin. `PUT /revocation` with a new `reviewSha256` disables that artifact. A later rollout, expiry or revocation removes the estimate on subsequent searches and history replays. Keep private dataset rows and reviews outside the API and Git. Synthetic and catalog data are suitable for conformance and exploratory comparison.

### Index and maintenance

On a reviewed pgvector deployment, apply the index DDL after Flyway as the approved owner. Run it in autocommit with stop-on-error. Set `DZOKA_MATCHING_VECTOR_BACKEND=pgvector-indexed` only after the index is valid. The HNSW expression index serves 384-dimensional non-truncated text components and is maintained by PostgreSQL when authoritative rows change. Verify `pg_index.indisvalid` and `indisready` and measure target recall before cutover. If an interrupted build leaves an invalid index, have the owner remove that exact invalid index concurrently and apply the reviewed script again. Keep independent scoped recall tests during maintenance and rebuild. The selected indexed route fails visibly when the extension or index is unavailable. Above the exact pool limit, separate indexed routes consider the authorized text, geographic, temporal, category and identifier candidates. The GIN text shortlist uses PostgreSQL lexical relevance before application scoring and reports approximation. Plan a migration window for the transactionally built report indexes on a large existing database. [Index DDL](../../tools/m5_install_pgvector_index.sql).

For Qdrant, provision a cosine collection per space before activation. Give the core a read-only Qdrant key in `DZOKA_MATCHING_QDRANT_API_KEY` and the scoped reconciliation writer key in `DZOKA_MATCHING_QDRANT_WRITE_KEY`. A principal with `matches:maintain-projection`, `reports:read`, and `reports:read:any` may call `PUT /api/v1/tenants/{tenant}/internal/matching/projections/{space}`. It upserts the tenant’s active components in bounded batches and deletes stale points only within that tenant and space. A failed pass can be replayed idempotently. Schedule the operation after rollout changes, revisions, and erasures, plus regular reconciliation. A disabled but retained space can be reconciled to an empty set. Retire a whole collection under the database and projection operator’s separate lifecycle controls. [Qdrant key permissions](https://qdrant.tech/documentation/operations/security/).

### Durable history

Use `PUT /api/v1/tenants/{tenant}/internal/matching/reports/{report}/runs/{run}` with a client-generated UUID and an object containing optional `spaceId`, optional `category` and `limit` (1–20). Repeat the same UUID and parameters within the 24-hour retention window to replay the saved result. Changed parameters conflict. Use `GET` on the same URI to retrieve a recorded search. Each actor has an independent UUID namespace and a retained-run cap of 100. A referenced report that is expired, superseded, deleted or outside current scope returns 404. Replay also requires the joint evidence pins and any associated sanitized media to remain available. An erased source revision cascades the run, and an erased candidate revision cascades its candidate row and invalidates replay. The ledger stores scored evidence and opaque references. Source text, protected digests and raw vectors are omitted.

Call `POST /api/v1/tenants/{tenant}/internal/matching/history/prune` with `matches:maintain-history` to remove up to 200 expired runs per call. The matching maintenance runner accepts a protected hash-bound JSON plan with `schemaVersion`, `origin`, `allowLoopbackHttp`, and `assignments`, each containing `tenant`, `spaces`, and `pruneHistory`. Run `python -B tools/matching_maintenance.py --plan <file> --sha256 <digest> --credentials <file>` with an independently issued Core JWT in the private `token` field. Use an approved scheduler and have it alert on an incomplete pass. The runner is serial and bounded and reports aggregate completion counts. Target scheduler, credential rotation and alerting need deployment configuration.
