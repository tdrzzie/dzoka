# M6 private claims and trusted recovery verification

The Core uses existing tenant memberships, report revisions, audit and outbox facilities. A new Flyway migration creates the enrollment, claim, evidence, verification, review, grant, activity and custody-return records. A report trigger serializes revisions, holds, expiry and tombstones with release and invalidates prior evidence through the report version. The logical restore verifies trigger definitions alongside row contents, roles, grants, row policies and indexes. [Implementation decision](../adr/0056-private-claims-and-accountable-pickup.md), [API and operations](../development/recovery.md).

The recovery suite uses a real PostgreSQL runtime role, separate migration role and signed local JWTs. It verifies the following.

- A representative claim requires separate entitlement evidence. Two active contenders cannot both proceed, even with correct private answers. Two independent reviewers with distinct corroboration meet dual control. Claimants and the challenge observer cannot approve the same claim.
- A private challenge contains a fixed prompt and expiry. Known public answers are rejected. Withdrawal invalidates an open session and prevents the same disclosed answer from being reintroduced. An actor's failures span sessions and items. An item's failure budget spans claimants. An unresolved challenge has an explicit inconclusive result.
- Current report and item holds, policy changes, revoked authority and expired tokens deny pickup. Only the designated authenticated desk can inspect the expected recipient. The return requires that exact recipient reference and a private confirmation reference.
- Two simultaneous pickups produce one return and one outbox event. An exact retry returns the same receipt even after throttling, while altered confirmation is refused. Failures, throttled attempts and replays have separate audit entries. Test assertions inspect persistence and outbound payloads for raw answers and tokens. A foreign tenant sees no report metadata through the restricted database function.

Source audit, architecture and 106 dependency pins passed verification. All 240 Python regressions and 27 Java unit tests passed. The native Core suite ran 84 integration tests with PostgreSQL, SeaweedFS, the Docker sanitizer and pinned text and vision providers. Its logical restore verified 52 tables and 4,790 rows. The separate indexed PostgreSQL suite ran 18 integration tests and restored 52 tables and 2,779 rows. Both used isolated services and had zero failures or skips. These suites cover the changed code paths. [Native restore](artifacts/m6-verification-20261118/native-restore.json), [indexed restore](artifacts/m6-verification-20261118/indexed-restore.json).

The locally verified workflow covers staffed handover with an opaque token and a private confirmation reference. Deployment acceptance needs institution-issued memberships, named desk operators, local secret management, independently approved retention controls and an on-site restore rehearsal. Role issuance, evidence outside the Core, and physical identity checks are institution procedures. Courier, messaging and signature capture are separate milestones.
